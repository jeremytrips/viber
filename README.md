# Viber

Viber is a native macOS app that runs Claude Code sessions as chats. It drives the real `claude` CLI in stream-json mode, so sessions use your normal Claude Code settings, hooks, skills, and transcripts, on your plain `claude` login or on Claude accounts Viber signs in to itself. Viber adds a sessions sidebar, chat UI, worktrees, cache and usage indicators, and notifications.

## Requirements

- macOS 14 or later
- Swift toolchain (Xcode 15.3+ or matching command line tools) to build
- The `claude` CLI on your PATH (`~/.local/bin`, Homebrew, npm and bun locations are searched too)
- Optional: `gh` for the `ship` and `cleanup` skills on GitHub. Without it, and on Bitbucket or GitLab, `/ship` gives the link that opens the pull request.
- Optional: Xcode with an iOS simulator runtime for the device panel. A physical iPhone also works once it is paired with this Mac (connect it once and tap Trust, or pair it in Xcode's Devices window) and has Developer Mode on
- Optional: the Android SDK (Android Studio, or Homebrew's `android-commandlinetools` with platform-tools and the emulator) for Android emulators and USB phones in the device panel. Viber looks in `ANDROID_HOME`, `~/Library/Android/sdk` and Homebrew's location. Google's [Android CLI](https://developer.android.com/tools/agents) is optional; Viber uses its `android layout` for screens uiautomator can't read

## Build and install

```sh
Scripts/build-app.sh   # builds dist/Viber.app (ad-hoc signed)
Scripts/install.sh     # builds, then copies it to /Applications (quit Viber first)
```

The build is ad-hoc signed, not notarized. If macOS blocks it, try opening it once, then use System Settings > Privacy & Security > Open Anyway.

## First run

Launch Viber from /Applications and allow notifications when asked. Notifications only work from the bundled app, not from `swift run`.

## Features

- **Projects**: the sidebar lists projects, with each one's open sessions under it and their state (working, waiting for you, finished, failed). Sessions started outside Viber show up too, below the projects.
  - **What a project is**: in a git repository, the main checkout's folder, so sessions in its subfolders and in its worktrees (Viber's, a hook's or ones made by hand) all sit under it. Viber finds it by following a worktree's `.git` file back to the repository. Outside git, the folder itself.
  - **Adding one**: ⇧⌘N, or the folder button next to *Projects* in the sidebar. Starting a session in a new folder adds its project too. A project stays in the sidebar when its last session closes; right-click it to rename it (only Viber uses the name) or remove it from the sidebar (its folder, issues and settings stay).
  - **Its page**: click a project to see its open sessions; its issues (Planning tab), with a field to add one; earlier sessions from the transcripts in `~/.claude/projects`, with **Resume** (dimmed when the folder, such as a removed worktree, is gone); its worktrees, with **Start Session** for one no session has open; its branches, newest commit first; and its settings (Settings tab): the account its sessions use (on Automatic, which accounts it may use), the issue key prefix, the branch pattern, the check after each request, the project's Claude Code settings files and CLAUDE.md, and the settings of a session that is open there. A folder that isn't a git repository yet can be made one there.
  - **Starting sessions**: the **+** on a project (shown on hover) or **New Session** on its page opens the New Session sheet on it. The sheet's **Projects** menu lists the sidebar's projects, then recent folders of others. Click the arrow to fold a project's sessions away; ⌘1–⌘9 count down the sidebar.
- **Chats with a project**: to ask how something works or plan the next piece of work without anything changing. Type in the **Ask about…** field at the top of a project's page, choose **New Chat** from its right-click menu or the speech bubbles next to it in the sidebar (shown on hover), or press ⌥⌘N. A chat is a session in the project's folder, marked with speech bubbles and *read-only chat*, and named after its first message.
  - **What keeps it read-only**: Claude starts without its tools that edit files (Edit, Write, NotebookEdit, and MultiEdit on older versions) and without plan mode, whose approval would switch to editing (`--disallowedTools`), in the mode that asks, whatever your settings or the New Session default say. Commands that only read (`git log`, `ls`, `grep`) run, and so do web searches and pages; anything else shows a permission card, and Always Allow there can't switch the mode. Claude Code only recognises simple commands in the project's folder as read-only (not `cd`, `git -C`, loops or `$(…)`, nor paths outside the project), so the chat's note asks Claude for one plain command per call and the Read, Grep and Glob tools for files. Commands your settings already allow (such as `Bash(npm run build:*)`) still run without asking, since Claude Code never asks Viber about them; the system prompt tells Claude not to run commands that change things. The mode menu shows *Read-only*, and `/plan` or `/auto` leave it as it is. A note added to Claude's system prompt says what the chat is for. Claude can't save memories in a chat either, since that needs Write.
  - **Planning**: when you want to keep a plan, ask Claude to add it as an issue: `viber issue` runs without asking in a chat (one of its session rules, with WebSearch and WebFetch, that you can remove under Permissions); on Jira, changes go through the Atlassian tools and ask as usual. Start the issue later to have a session do the work.
  - The check after each request doesn't run in chats. A closed chat resumed from **Earlier Sessions** (marked with the same bubbles) or the Resume sheet comes back read-only.
- **Chat**: streamed replies, tool calls summarized inline, Claude's thinking folded into a row you can open, stop with ⌘. The chat follows new text while you are at the end; scroll up to read and it stays where you are until you scroll back down or send a message. Return sends; Shift-Return (or Option-Return) starts a new line. Hover a message to copy it: the button sits left of your messages and in the margin of Claude's (your messages also have Copy Message on right-click).
- **Agents**: each subagent Claude starts gets a card. While it runs, the card shows its last step, tool count, tokens and time, and a Stop button. A smaller copy of the card stays pinned above the message box until the agent ends, so you can follow it without scrolling. A background agent stays running after the turn that started it. When it ends, its report shows on the card, Markdown-formatted and cut to a preview you can expand. Open the card to see the prompt Claude gave it and every tool call it made. When a background agent finishes, Claude reads its report in a turn of its own, which shows as working. Permission requests from an agent say which agent asks. Resumed sessions rebuild the cards from the agents' own transcripts.
- **Checklist**: when Claude keeps a task list (`TaskCreate`/`TaskUpdate`, or `TodoWrite` on older setups), it stays pinned above the message box until everything on it is done. Claude Code only offers these tools to current models when `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` is set (for example under `env` in `~/.claude/settings.json`).
- **Rewind files**: hover a message you sent (or right-click it) and choose rewind to put files back the way they were before it, like Esc Esc → restore code in the terminal. Viber shows which files would change and asks first; the conversation itself is left as it is.
- **Images and files**: paste (⌘V), drop or attach (paperclip) images to send them with a message; they are scaled to at most 2000 px. Other files and folders are mentioned as `@path`, and typing `@` offers the project's files (from `git ls-files`).
- **Cards** for permission requests, questions from Claude (`AskUserQuestion`), plans to approve (`ExitPlanMode`), and MCP servers asking for input (a form built from the server's schema, or a page to open in the browser).
- **Slash commands**: type `/` for a menu. Commands that only exist in Claude Code's terminal UI are handled by Viber:
  - `/plan [prompt]` switches to plan mode (and sends the prompt, if any)
  - `/model [name]` switches model, or opens a picker
  - `/clear` starts a fresh conversation in the same session
  - `/resume` opens the resume picker
  - `/cost` shows tokens and cost for the session
  - `/tasks` (or `/bashes`) opens the session's background tasks
  - `/add-dir <path>` lets Claude work in another folder for this session (bare `/add-dir` opens Permissions)
  - `/mcp`, `/context` (or `/usage`), `/permissions`, `/hooks` and `/settings` (or bare `/config`, `/effort`, `/output-style`) open the session's settings on that tab. With arguments, `/mcp reconnect all`, `/effort high` and `/config key=value` still go to the CLI, which handles them itself.

  Everything else (skills, custom commands) is sent to the CLI as text. Viber's own skills work as `/cleanup` as well as `/viber:cleanup`.
- **Session settings** (the sliders button in the session header, ⌥⌘, or the commands above) are the terminal panels for one conversation, drawn from the CLI's control requests:
  - **MCP**: every server with its status, tools and errors. Sign in (opens the browser; the row turns connected when you finish), retry, reconnect, sign out, and turn a server off or on. Like `/mcp` in the terminal, on/off is saved for the project. The browser page can say you're signed in when Claude then couldn't use the login, so a row still not connected 2 minutes after Sign In says so. Each account keeps its own Keychain item, so a sign-in to a server of your own holds for that account only (a chat moved to another account signs in again), and its row says so; claude.ai connectors sign in with each Claude account. The header shows "MCP 5/7", orange when a server needs sign-in or failed.
  - **Context**: where the context window goes, by category, plus the session's cost. Compact now, with optional instructions.
  - **Permissions**: the rules in effect and where each comes from. Add or remove a folder Claude can work in for this session (like `/add-dir`), and add or remove a rule for *this session* (kept across relaunches, gone when the session closes), *this project, just me* (`.claude/settings.local.json`, which Viber keeps out of git) or *this project, shared* (`.claude/settings.json`). Claude Code picks file changes up right away.
  - **Hooks**: every hook that runs, from settings files and plugins. Read-only; buttons open the settings files.
  - **Tasks**: shell commands Claude runs in the background, subagents and monitors, running and recently finished. Read a shell's output (kept current while open) or stop a task. The header shows "Tasks 2 running" while any run.
  - **Model**: model, effort and permission mode for this session; output style, saved for the project.
- **Settings** (⌘, or the gear at the bottom left of the sidebar) hold everything that is not about one conversation:
  - **General**: which notifications to post, how early to warn about cache expiry, whether to continue sessions after a usage limit, and the permission mode new sessions start in.
  - **Permissions** and **Hooks** in `~/.claude/settings.json`, for every project.
  - **MCP** servers for every project (`claude mcp add/remove --scope user`).
  - **Model**: the model new sessions start with, and the default effort per model.

  Changes to these files apply to sessions started afterwards.
- **Messages between sessions**: start a message with `//` to send it to another open session instead of this one. A menu ranks the other sessions by what you typed (their title, project, branch and recent conversation), so `//the firmware endpoint is ready` goes to the session working on firmware. Start with a session's name (`//backend: …`) to pick it directly, or use ↑↓ to choose. The receiving session shows who it came from. If it is busy, Claude reads it after the tool call it is running, like a message typed while it works. Its answer is posted back into the sender's chat (marked "Reply from …") so the sender's Claude can carry on; replies never ask for an answer, so sessions don't ping-pong. Messages live only in the two chats they touch: the sender's "Sent to …" line shows whether the message is not read yet, waiting for a reply, replied or got no reply.
- **Issues**: each project's work, as a list in Viber (not in the repo): issues to do, in progress, in review and done, each with a key such as `EST-12` (the prefix comes from the folder's name; change it in the project's Settings tab). Click the list button next to a project in the sidebar (shown on hover until there is one) to add an issue or see the ones not done (the number is how many are to do); the project's **Planning** tab shows them all, grouped by status or as a board whose cards you drag between columns. The **Issues** panel (top of the sidebar, ⇧⌘I) shows every project's issues, filtered by status, with search. **Start** opens a new session for an issue in plan mode, in a new worktree when the project is a git repo, with the issue, its notes and what it is part of or blocked by as the first message; `<key>` in the branch pattern becomes the issue's key, and a pattern without it puts the key in front of the slug (`viber/est-12-docker-image`), so a session's issue can be read from its branch, also for worktrees made by hand. Starting a blocked issue asks first. An issue can be part of another (sub-issues) and blocked by others; right-click → Edit sets both, and notes can be added to any issue. Statuses follow the sessions: Start → in progress, `/ship` → in review (`viber issue shipped`), `/cleanup` after the merge → done, and `viber issue done` from a session. The sidebar shows each session's issue and status. Sessions add issues with `viber issue add` (the `/issue` skill); each shows who added it. Ideas from earlier versions became issues, and project notes before that became one issue each.
- **Jira**: a project can read its issues from Jira instead (its Settings tab → Tracker). Add the site once in Settings → Jira (⌘,): the site, your email and an API token with the read-only scopes, kept in the Keychain; **Test** checks it. The project then gets **views**, JQL queries shown one at a time on its Planning tab (*My issues*, *Current sprint* and *Backlog* to start with; edit them or add more), loaded 50 at a time with **Load More**, searched within the view, and read again every minute. A view **by epic** loads only the epics and the issues outside them, and an epic's issues when you open it, so a long backlog stays small. **Start** on an issue opens a session in a new worktree whose first message is the tracker's **On Start** text, `/work-issue <key>` by default, so the repository's own skill takes it from there; the issue's summary and description follow. Viber only reads Jira: every change (moving an issue, a comment, a new ticket) goes through Claude and the repository's skills. The sidebar shows a session's Jira issue and status, read from its branch (`feat/nex-224-…`), and `<key>` in the branch pattern becomes the issue's key. **Draft…** writes a line you type up as a Jira ticket: a session reads the project's Jira rules (such as a `jira-tracker` skill), searches Jira for the same work, reads the code it touches, then calls the Atlassian tool to create the issue; Viber shows that call as a ticket you can edit (project, type, priority, summary, description, labels) and **Create** or **Cancel**, so nothing reaches Jira before you have seen it. The same card appears whenever any session asks to create a Jira issue. Viber's own issue list and `viber issue` stay available, but a Jira project's Planning tab shows Jira.
- **Ask Claude**: a menu on the Issues section (both trackers) that starts a session in the project with a prompt for one job: **Review the Backlog** (folds duplicates, closes what is already on the main branch, lists stale issues, sizes the rest from the code), **What's Next?** (one issue to start now and why; changes nothing) and **Standup Note** (yesterday, today, blocked, as a draft to paste; changes nothing). Right-click an issue → **Break Down with Claude** for sub-issues it finds in the code. On Viber's own list Claude makes the changes directly with `viber issue`; each shows at once and can be undone. On Jira every call to the Jira servers asks first.
  - **Autopilot on Jira**: **Autopilot…** on an epic (in a view by epic) or the airplane next to a view's search takes the issues that are to do and yours or unassigned (epics, decisions and other people's issues are left out, and the sheet says why), several at a time, each in a new worktree with a session whose first message is the tracker's **On Start** text, so the repository's own skill does the work and moves the issue. Each session commits on its branch (after the tests and `/code-review` when the project's **After each request** is on) and stops at the skill's "landed, not merged" status; nothing is pushed or merged, and you ship each branch yourself. Every call to the Jira MCP servers named in the tracker's settings asks in those sessions: Viber allows reads, and moving or commenting on the issue the session is on, and holds anything else (a new issue, another issue, Done, Wontfix) as a prompt in the session, pausing the run until you answer it. Sessions report with `viber issue done` or `viber issue failed`, which on a Jira project refer to the key in the branch. The card shows each issue it is on, with Skip, and what each reported; the worktree cap and pauses work as for Viber's own autopilot.
- **Check after each request**: turn on **After each request** in a project's Settings tab, and when a session there finishes a request that changed files, Viber sends it one more message: run the tests (the command in **Tests**, or the way the project's CLAUDE.md or build files say when that is empty), run the `code-review` skill on the request's changes, fix what fails and the findings Claude agrees with, run the tests again, and report what it fixed and what it left. The session keeps working through the check, so its "Finished" notification comes once the check is done. A request is done once Claude's background agents are through too. Whether it changed files comes from git (Viber compares the checkout before and after, so edits made with shell commands count) and, outside git, from Claude's edit tools. A request you stopped, one that failed and one that changed nothing are not checked, and what the check itself changes isn't checked again. Commits are left to the request: the check commits its fixes on top of work that was already committed, and never pushes. Autopilot sessions (on Viber's issues and on Jira) get it as a step of their own instead, before they ship or commit, since they ship within one turn; the Autopilot sheet says whether it is on. Saved in Viber, not in the repository.
- **Usage limits**: when a session stops at your plan's session (5-hour) or weekly limit, Viber reads when the limit resets from Claude Code's own report, waits, and a minute after the reset tells Claude to carry on where it left off. Meanwhile the sidebar shows an hourglass on the session, and a bar above its message box says when it continues, with **Continue Now** and **Don't Continue**. Sending a message yourself replaces the wait. If the limit is still there after the reset, Viber tries again a few minutes later, and gives up after four tries in a row. Waits survive relaunching Viber. Turn it off in Settings → General.
- **Autopilot**: implements a project's issues to do while you're away, several at a time. Start it with **Autopilot…** in the Issues section of the project's Planning tab or the airplane in its issues popover (for every issue to do, oldest first), or right-click one issue → **Implement on Autopilot…**. The sheet picks what happens once an issue works: **open a pull request** (each session pushes its branch and opens one, as `/ship` does; every issue starts from origin's default branch), **merge it** into the branch checked out in the project's folder (each session merges that branch in, checks again and fast-forwards it, so the next issue builds on the last; nothing is pushed), or **commit it** on its branch for you to review. It also picks the mode (Auto mode by default), the account, how many **sessions at once** (1 to 8; 3 by default) and the most **worktrees** the project may have open (8 by default).
  - **Each issue** gets a new worktree and a session in it, started without taking you there. Its first message is the issue and the steps: implement it without asking, keep to it (anything else goes to `/issue`), run the project's checks (and, when the project's **After each request** is on, the tests and `/code-review`, fixing what they find), ship it, then report with `viber issue done "<what shipped>"` or `viber issue failed "<why>"`. The project's rules come first. A report frees its place for the next issue. An issue blocked by another in the run waits for it to ship; when the run commits or opens pull requests, the dependent issue's worktree then starts from the blocker's branch, since it isn't merged yet. The run needs a git repository; a branch pattern with a part only you know (`<id>`) or without `<slug>` is replaced by `viber/<slug>`.
  - **While it runs**, the project's page and popover show each issue it's on (with **Skip**), how many are done, stuck and to go, and the sidebar marks the project and the session with an airplane. Each issue shows its place in line, then what its session reported: a summary when done, or why it got stuck (a stuck issue stays in progress, linked to its session). Issues you add meanwhile join the end of the line; ones its sessions add wait for you, so a run can't feed itself. A shipped issue keeps its worktree until it is merged and cleaned up; once the project has as many worktrees open as the run allows, the card says so and the run continues when one is closed, so it can't get further ahead of you than that.
  - **When a session stops without a report**, the autopilot waits while its background commands or agents run, then reminds it twice; a third stop counts the issue as stuck and moves on. A session idle 15 minutes is reminded even while a background command runs, in case it never ends. A session waiting for you (a permission, a question) holds the run until you answer.
  - **At a usage limit it waits**: the card says when the session carries on, and the run resumes by itself once the limit resets (unless that is turned off in Settings → General, or you choose *Don't Continue* in the session).
  - **It pauses** (with a notification) when a session's turn fails (an API error, a dead login), when you stop a session, when a worktree can't be made, and after three stuck issues in a row. A pause stops new issues from starting; the sessions already going carry on. **Resume** tells idle sessions to carry on and starts the next issues. **Stop** offers *Stop After These Issues* and *Stop Now*; skipped and stopped sessions are interrupted and stay open. Closing an active session, or marking its issue done, moves the run on. A run ends when no issue is left, and doesn't survive quitting Viber.
- **Browser preview** (the Safari button in the session header, ⇧⌘B): a browser beside the chat that you and Claude share, so Claude can check its own web work.
  - **Viber serves the tools itself.** They come from an MCP server built into Viber, over the same stdio channel, so there's nothing to install. Every session gets them.
  - **The tools:**
    - `preview_open` loads a dev server URL.
    - `preview_screenshot` captures the page. It first waits for the hot update after Claude's last edit (Vite, Next.js, webpack), then for the page to settle.
    - `preview_snapshot` gives an outline of the page with element refs.
    - `preview_console` returns console output, uncaught errors and failed requests.
    - `preview_click`, `preview_type`, `preview_eval` and `preview_wait` act on the page.
  - **Permissions:** looking never asks. Clicking, typing and scripts are approved automatically on local pages, and ask anywhere else. Both are configurable under Settings → General.
  - **Pick an element (⇧⌘C).** Click something in the page and it is attached to your next message, with its selector, HTML and, for React, Vue and Svelte dev builds, the component and source file. So "make this bigger" edits the right code.
  - **Handy extras:**
    - When a command prints a local URL (a dev server starting), its row offers *Open in preview*.
    - The console button shows errors since the last load.
    - The page keeps running while you look at other sessions, and the URL is restored after a relaunch.
- **Device panel** (the iPhone button in the session header, ⇧⌘D): an iOS simulator, an Android emulator, a USB Android phone or an iPhone beside the chat that you and Claude share, so Claude can check its own app work.
  - **It runs inside Viber.** The device's screen streams into the panel. Click and drag to touch, scroll to swipe, and type when the screen has focus (⌘V pastes your Mac clipboard). Simulator.app doesn't need to be open, and emulators run without their own window. Pick a device from the menu at the top left; it boots if it is off. Devices are shared, so two sessions can show the same one.
  - **The tools:**
    - `device_open` boots and shows a device ("iPhone 17", "Pixel 8"); `device_list` lists them.
    - `device_install` and `device_launch` run a `.app` built for the simulator or an `.apk`. `device_open_url` opens deep links and `exp://` URLs for Expo Go; on Android it forwards `localhost` ports to the Mac first.
    - `device_screenshot` captures the screen, one pixel per point (per dp on Android). `device_snapshot` gives an outline of the screen's accessibility tree with element refs.
    - `device_tap`, `device_swipe`, `device_type` and `device_press` (home, lock, volume; Siri on iOS; back and recent apps on Android) act on it. `device_wait` waits for text, and `device_logs` reads the log.
    - `device_set` changes settings without going through the Settings app: light or dark appearance, a simulated location (simulators and emulators only), permissions granted to an app without the prompt, and a clean status bar for screenshots (9:41, full battery and signal).
  - **Permissions:** looking at a simulator or emulator never asks, and tapping, typing, installing, launching and changing settings are approved automatically there (both configurable under Settings → General). A physical phone holds real data: Claude's tools only use one you chose in the panel or that Claude names, looking at it asks unless you chose it, and acting on it always asks.
  - **Pick an element** (the arrow button) attaches what you click to your next message, with its label, accessibility identifier and frame. The camera button attaches a screenshot.
  - **Run on device**: when a command's output shows a simulator build (`…-iphonesimulator/MyApp.app`), an Android build (`…/build/outputs/apk/…/app-debug.apk`), an Expo Go URL (`exp://…`) or a development build's link (`exp+myapp://expo-development-client/?url=…`, from `expo start --dev-client`), its row offers to run it in the panel. A development build has to be installed on the device first. Run without a terminal, as through Claude's Bash tool, Expo prints no link, only `Waiting on http://<ip>:8081`; Viber then forms the link as Expo would from the app in the folder Expo started in (else the session's): a development build's when the app depends on `expo-dev-client`, with the `exp+` scheme in `ios/<app>/Info.plist` (or the Android manifest), else `exp+<slug>` from `app.config` or `app.json`; otherwise Expo Go's.
  - **How it works on Android:** the live screen and input use the server of [scrcpy](https://github.com/Genymobile/scrcpy) (Apache-2.0, license in `ThirdParty/scrcpy`), version 5.0.1, which `Scripts/build-app.sh` downloads and checks against a pinned SHA-256. Viber pushes it to the device over adb, decodes its H.264 stream with VideoToolbox and sends touches and keys over its control socket. Everything else goes through adb: `screencap`, `uiautomator dump`, `am start`, `adb install`, `logcat`, and for `device_set` `cmd uimode night`, `emu geo fix`, `pm grant` and SystemUI's demo mode. Emulators boot with `emulator -no-window`. When running from the repo (`swift run`), run `Scripts/fetch-scrcpy-server.sh` once for the live screen.
  - **How it works on iOS:** the live screen, touches, keys and the accessibility tree use Apple's private CoreSimulator and SimulatorKit frameworks, loaded at runtime, in the way [idb](https://github.com/facebook/idb) (MIT) and [serve-sim](https://github.com/EvanBacon/serve-sim) (Apache-2.0) do; Viber's bridge follows their code. Everything else goes through `xcrun simctl`. If an Xcode update breaks the private part, the panel says so and Claude's tools fall back to `simctl` where they can. Xcode 27's simulators ignore that input, so there touches, keys and buttons go over XPC to the simulator's own `dtuhidd`, again as idb does.
  - **Physical iPhones:** paired iPhones and iPads that are nearby, on USB or on the same Wi-Fi, appear in the device menu. `xcrun devicectl` installs apps built and signed for devices (`Debug-iphoneos`), launches them and opens links (in Safari, in Expo Go, or in an app that claims the URL's scheme). Over USB the panel shows the live screen and Claude can take screenshots; this uses the same public CoreMediaIO and AVFoundation path as QuickTime's iPhone recording, so macOS asks to give Viber Camera access the first time. Over Wi-Fi there is no picture. `device_logs` returns the output of apps Viber launched (print, NSLog and os_log), because reading a phone's system log needs root. Nothing public can send touches or keys to a phone or read its accessibility tree, so the tap, swipe, type, press, snapshot and wait tools refuse, as does `device_set`, and Claude asks you to use the phone.
- **Worktrees**: start a session in a new git worktree, so parallel sessions don't collide.
  - **Branch**: the New Session sheet's Branch field starts as the project's branch pattern filled in with the session name, and follows the name until you edit it. The pattern is `viber/<slug>` until you set another with **Pattern…** next to the field (Viber saves it per repository, not in the repository). `<slug>` becomes the session name; other parts, such as `<id>` in `feat/NEX-<id>-<slug>`, are left for you to replace, and Start waits until you have. Viber checks a typed name with `git check-ref-format --branch` and that no branch by that name exists yet. An untouched default is numbered after the slug (`viber/login-2`) if taken.
  - **With git** (the default): the worktree is `<repo>/.claude/worktrees/<slug>` on that branch. Gitignored files that the project's `.worktreeinclude` lists (`.gitignore` syntax, such as `.env`) are copied into it, as Claude Code does.
  - **Where it starts**: like Claude Code, from origin's default branch (`origin/HEAD`, else `origin/main` or `origin/master`), after a `git fetch` of it that gives up after 8 seconds and never asks for a password; offline, the cached ref is used. **Start from** in the sheet can pick the branch checked out in the folder instead. Without an origin, it starts from the current branch. The new branch doesn't track `origin/main`, and the base is recorded so the diff stat in the sidebar compares with it. A `WorktreeCreate` hook chooses its own starting point.
  - **With the project's own setup**: when the folder's Claude Code settings define a `WorktreeCreate` hook, Viber runs it instead of `git worktree add`, as `claude --worktree` would. Viber reads the same settings files Claude Code does for that folder (`~/.claude/settings.json`, the folder's `.claude/settings.json`, `.claude/settings.local.json` at the repository root, and managed settings), and respects `disableAllHooks` and `allowManagedHooksOnly`. The hook gets JSON on stdin with `cwd` and the branch as the worktree `name` (the field Claude Code uses, so the name must also fit Claude Code's rule for worktree names: letters, digits, `.`, `_`, `-` and `/`), runs in the folder with `CLAUDE_PROJECT_DIR` set, and prints the new worktree's path as the last line of its output (everything else goes to stderr). Viber reads the branch from the worktree's HEAD. `.worktreeinclude` isn't applied then; the hook copies what it needs. Viber runs command hooks only; it says so if the hook is an HTTP or MCP tool hook. The New Session sheet shows the command that will run.
  - **While it's made**, the session shows in the sidebar with the setup's output as it arrives, and a Stop button. A hook stops after its `timeout` (600 seconds by default, as in Claude Code). If setup fails, its output stays there with **Try Again**, and no session starts.
  - If the folder isn't a git repository yet, **Create One** in the New Session sheet runs `git init` and commits a README titled after the folder.
  - Closing can remove the worktree (refused if it has uncommitted changes) and delete the branch (only when it is merged into the branch it started from, the default branch or the main checkout's current one, so unmerged branches are kept). For a worktree a `WorktreeCreate` hook made, the project's `WorktreeRemove` hook removes it when there is one (it gets the `worktree_path` on stdin, and can stop the worktree's containers first); otherwise, and for worktrees made with git, `git worktree remove` does, as in Claude Code. The close dialog shows the hook. While it runs, the removal shows in the sidebar with its output; if the hook fails and the worktree is still there, it is kept, and the sidebar says why, with **Try Again**.
- **Cache ring**: time left on the prompt cache per session; Viber can warn before it expires.
- **Accounts**: add each Claude account once under the toolbar's account button (**Add Account…**: a name, the address to sign in with, and whether Automatic may use it). Viber runs `claude auth login` in the account's own folder (`~/Library/Application Support/Viber/accounts/<name>`, used as `CLAUDE_CONFIG_DIR`), which opens the browser. That folder links everything else to `~/.claude`, so settings, plugins, memory and transcripts are shared and any account can resume any session; `~/.claude.json` is copied in at each start, keeping the account's own identity. The login stays: running sessions refresh their token, and Viber refreshes an idle account's with its refresh token. Right-click an account to log in again, keep it out of Automatic (a personal account), or remove it. If the signed-in address is already another account's, Viber says the browser was on the wrong account.
- **Usage bar**: each account's 5-hour and weekly usage, read from Anthropic every two minutes and from running sessions as they go.
- **Account per project**: each project picks the login its sessions start with: **Automatic** (the default), one account, or plain `claude`. Set it on the project's Settings tab, or under the toolbar's account button, which shows the selected project's account. New sessions, Ask Claude, Jira sessions and autopilot runs there use it. When open sessions run on another account, Viber asks whether to move them: each restarts Claude on the new account with `--resume`, in the mode it is in, so the conversation stays; a busy one moves once it's done (after the check after each request, when the project has one), and one waiting out a usage limit carries on at once. An account with a broken login stays chosen (log in again from the account button) rather than falling back to another account.
- **Automatic**: each session starts on the account Automatic may use with the least-used week, among those with room (under 90% of their 5 hours and 95% of their week). Accounts within 10 points of that week count as tied, and the one running the fewest sessions wins, so chats started together spread out. Untick accounts under **Automatic uses** on a project's Settings tab (or in the account popover) to keep that project off them; sessions already there are offered a move. When a session's account hits a limit, or is almost out of room after a turn, Viber moves it to another account with room with `--resume`, and carries on if it was stopped. A restart keeps a session where it is while its account has room. Accounts kept out of Automatic, such as a personal one, are only used when chosen in New Session or as a project's account.
- **Notifications** when a session finishes or needs you; clicking one opens that session.

## The `viber` CLI and skills

Viber puts a small `viber` command on the PATH of every session it starts (with `VIBER_PANE_ID` set), and loads its plugin with `--plugin-dir`. Skills use the CLI to talk back to the app:

```sh
viber close [--remove-worktree] [--delete-branch]   # close this session after the current reply
viber worktree                                      # print the worktree Viber made for this session (path, branch, repo)
viber notify <text…>                                # post a notification
viber rename <title…>                               # rename the session in the sidebar
viber issue                                         # print this session's own issue (exit 1 if none)
viber issue list                                    # print this project's issues that are not done
viber issue show <key>                              # print one issue with its links and notes
viber issue add [--parent <key>] [--blocked-by <key,…>] <text…> | add -   # add an issue (`-` reads stdin); the first line is its title
viber issue update <key> [--status todo|progress|review|done] [--parent <key>|none] [--blocked-by <key,…>|none]
viber issue comment <key> <text…>                   # add a note to an issue
viber issue done [<what shipped…>]                  # mark this session's issue as done
viber issue failed <why…>                           # say it got stuck and why; it stays in progress, linked to this session
viber issue shipped [<what landed…>]                # move this session's issue to in review (/ship does this)
```

Outside a Viber session it exits with status 2.

Skills in `plugin/skills`:

- `/cleanup`: checks that the branch is merged (including squash merges via `gh`), with no uncommitted changes, unpushed commits, or stashes, then asks Viber to remove the worktree and branch. It only does so for the worktree Viber made for this session (`viber worktree`), wherever it is and whatever its branch is called. It never deletes anything itself.
- `/ship`: reviews the diff, runs the project's required checks, commits, asks before pushing, then opens a PR with `gh` on GitHub, or gives the pull or merge request link on Bitbucket and GitLab. Commit format, checks and push rules from the project's `CLAUDE.md`, `AGENT.md` or skills come first.
- `/sync`: brings the branch up to date with the latest base branch: rebases a branch that was never pushed, and merges the base into one that was (unless the project's rules say otherwise). Resolves conflicts carefully, runs the project's checks, and never force-pushes without asking.
- `/handoff`: writes a status note (goal, done, in progress, next steps, open questions, files touched).
- `/issue`: saves an idea, follow-up or out-of-scope task as an issue in the project's list, written so a later session can plan it without this conversation, optionally as a sub-issue or blocked by another. Claude also uses it on its own when it notices work outside the current task.

## Development

```sh
swift test
VIBER_PLUGIN_DIR=$PWD/plugin swift run Viber
```

`VIBER_PLUGIN_DIR` and `VIBER_BIN_DIR` override the plugin and `viber` CLI locations that are otherwise taken from the app bundle. For the CLI in dev, build it with `swift build --product viber-ctl` and point `VIBER_BIN_DIR` at a directory containing it named `viber`. Notifications need the bundled app (`Scripts/build-app.sh`).
